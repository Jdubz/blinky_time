# Bypass the bootloader, let the app update

> **Research input (2026-10-20), not the current design.** It describes the firmware as it was before PR #257: the unsigned, CRC-only `ota begin/chunk/commit` commands. What was built from it is in [WEB_FLASHER.md](WEB_FLASHER.md):
> - signed OTA via `ota manifest/chunk/commit`, with Ed25519 signing, board and load-address checks, and anti-rollback;
> - signing only after the bench gate;
> - a USB and Bluetooth page.
>
> Hub-driven updates were deliberately skipped for now. Keep this for the platform constraints, especially iPhone, Windows and UF2, and for the options that were weighed.

Consumer firmware updates for the XIAO nRF52840 should stop going through the bootloader. The firmware already has a path where the running app receives the image (`ota begin/chunk/commit`), stages it in QSPI, and asks the bootloader to apply it. A browser can drive that path over **Web Serial on desktop Chrome/Edge (and Firefox 151+)** and over **Web Bluetooth to the app's Nordic UART service on Chrome/Edge for Windows, macOS, Android and ChromeOS**. Neither touches the UF2 drive that Windows breaks, and neither touches the legacy DFU service that Chrome blocklists. iPhone is the gap. Safari has no Web Bluetooth and WebKit opposes adding it, so iPhone owners need either the fleet's BLE hub, which can update a device with no owner action, a third-party Web Bluetooth browser (Bluefy), or eventually a small native app. Two things matter more than the choice of transport. First, the staged image is checked only with a CRC, so any page or any nearby BLE central that speaks NUS could stage arbitrary firmware. **Signature verification, a hardware ID check and anti-rollback must exist before any public updater ships.** Second, the bootloader's stuck-transfer check should be narrowed so UF2 works as a technician recovery path, but it should not be the consumer path. For a one-person project, the smallest set that reaches every owner is: hub-driven automatic updates, one web page using NUS and Serial, and Bluefy documented for iPhone. A native app waits until real iPhone demand appears.

## The UF2 drive and legacy DFU are dead ends for consumers

The first flasher failed for structural reasons, not because of a fixable bug in the page. Upstream Adafruit ghostfat ignores every sector that is not a UF2 block (`if (!is_uf2_block(bl)) return -1;`) and has **no timeout in its write path**. It tracks completion with a `writtenMask` checked against `numBlocks` ([ghostfat.c](https://raw.githubusercontent.com/adafruit/Adafruit_nRF52_Bootloader/master/src/usb/uf2/ghostfat.c)). The UF2 spec explicitly expects "OS writing data that is not UF2 blocks". Its "reset after ~1 s break in incoming UF2 blocks" idea is an alternative to bitmap tracking that applies only once blocks are flowing ([microsoft/uf2](https://github.com/microsoft/uf2)). The fork's `msc_uf2_check_stuck()` arms on host writes that contain no UF2 data, which is why a Windows System Volume Information write on mount trips it. No public source documents this failure. It is specific to our 0.8.0-10 patch. The right fix is to arm the timer only after the first valid UF2 block, only while `0 < numWritten < numBlocks`, and to reset it only on valid blocks. That fix is a bootloader change and goes through `deploy-bootloader.sh`.

Even fixed, UF2 is a poor consumer path. Prior art treats copy errors as normal. ZMK, the largest nRF52840 UF2 user base, tells users that Finder error -36 and "fcopyfile failed" on macOS Sonoma "can be ignored" ([ZMK](https://zmk.dev/docs/troubleshooting/flashing-issues)). Adafruit has fixed Windows 0x800701B1 and incomplete-write errors in the bootloader over the years ([Adafruit #120](https://github.com/adafruit/Adafruit_nRF52_Bootloader/issues/120); [changelog](https://github.com/adafruit/Adafruit_nRF52_Bootloader/blob/master/changelog.md)). UF2 has no hash or signature beyond per-block magic numbers. It writes internal flash directly, so the old app is gone as soon as the copy starts. Phones cannot reach the drive. Meshtastic, the closest match to our hardware, still labels drag-and-drop as its "recommended" nRF52 path, and its web flasher only downloads and copies the file ([Meshtastic drag & drop](https://meshtastic.org/docs/getting-started/flashing-firmware/nrf52/drag-n-drop/)). Nobody has made one-click browser UF2 work well on nRF52.

The bootloader's BLE route is closed to browsers by design. The Web Bluetooth GATT blocklist fully blocks `00001530-1212-efde-1523-785feabcd123`, Nordic legacy DFU, because it does not check signatures. Secure DFU (`0xFE59`) and NUS (`6e400001-…`) are not blocklisted ([gatt_blocklist.txt](https://raw.githubusercontent.com/WebBluetoothCG/registries/master/gatt_blocklist.txt)). Moving the fleet to Secure DFU would mean replacing an SDK 11 bootloader ([Adafruit source tree](https://github.com/adafruit/Adafruit_nRF52_Bootloader/tree/master/lib/sdk11/components/libraries/bootloader_dfu)) with one that needs about 24 kB instead of about 15 kB. Nordic calls the workaround for that size change "not fail-safe" if the device resets mid-update ([DevZone 65611](https://devzone.nordicsemi.com/f/nordic-q-a/65611/updating-legacy-bootloader-sdk-11-0-with-latest-secure-bootloader-sdk-17-0/268457)). Adafruit's own signed-firmware option disables UF2 entirely ([Adafruit README](https://raw.githubusercontent.com/adafruit/Adafruit_nRF52_Bootloader/master/README.md)). Upstream 0.11.0 also has an open regression (#399) in which BLE OTA wedges after Start DFU and leaves the device without an app ([Adafruit #399](https://github.com/adafruit/Adafruit_nRF52_Bootloader/issues/399)). That is a warning against rebasing the fork casually. Driving adafruit-nrfutil serial DFU from Web Serial is technically possible, but it inherits single-bank app invalidation and a timed transport handshake. The 2021 serial-DFU timeouts were a TinyUSB race that has since been fixed ([Adafruit #195](https://github.com/adafruit/Adafruit_nRF52_Bootloader/issues/195)), but the structural risks remain.

## App-mode staging reaches four of five platforms with no install

The QSPI-staged OTA is already the safer architecture. It has the same shape as MCUboot overwrite-only with an external secondary slot, which Nordic documents for the nRF52840 with QSPI ([MCUboot design](https://docs.mcuboot.com/design.html); [NCS external flash](https://developer.nordicsemi.com/nRF_Connect_SDK/doc/v1.6-branch/nrf/ug_bootloader_external_flash.html)). The old app keeps running for the whole transfer, so a dropped cable or BLE link costs only a retry. The only risky window is the bootloader's QSPI-to-internal copy, which takes about 10–15 s. That figure is estimated from datasheet timings and has not been measured. There is no reboot into a bootloader with a different identity until commit, so the browser never has to re-pick the device mid-update.

| Platform | Wired path | Wireless path | Notes |
|---|---|---|---|
| Windows 10/11 | Web Serial, Chrome/Edge 89+, Firefox 151+ | Web Bluetooth, Chrome/Edge (Win10 1703+) | Native CDC uses the inbox driver; no CH340-style driver problems |
| macOS | Web Serial, Chrome/Edge, Firefox 151+ | Web Bluetooth, Chrome/Edge | Safari has neither; show a "use Chrome" prompt |
| Android | Web Serial over USB is in the Chrome 148 notes, but rollout is unclear | Web Bluetooth, Chrome (Android 6+) | BLE is the real path; the PWA already uses it |
| ChromeOS | Web Serial | Web Bluetooth | Same as desktop |
| iPhone/iPad | None | None in any App Store browser engine; only Bluefy or the beacio Safari extension | Hub update, wrapper browser, or native app |

Sources for the table: Web Serial has shipped on all desktop Chromium platforms since Chrome 89 ([Chrome docs](https://developer.chrome.com/docs/capabilities/serial)). Firefox 151 (May 2026) added Web Serial with an add-on-style gating prompt ([Mozilla Hacks](https://hacks.mozilla.org/2026/05/web-serial-support-in-firefox/)). Web Bluetooth GATT is unflagged on Windows, macOS, Android and ChromeOS, and iOS Chromium has "no implementation planned" ([implementation status](https://github.com/WebBluetoothCG/web-bluetooth/blob/main/implementation-status.md)). Chrome 148's release notes list "Web Serial API on Android" for USB devices ([Chrome 148](https://developer.chrome.com/release-notes/148)), but the ChromeStatus record still read "Proposed" when the researchers checked ([ChromeStatus](https://chromestatus.com/api/v0/features/6043992171085824)). Treat Android wired as unconfirmed. Web Serial's Bluetooth mode is RFCOMM, which cannot reach a BLE-only NUS device. WebUSB and WebHID add nothing here. WebUSB cannot claim Mass Storage on any OS ([blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/LZXocaeCwDw/m/GLfAffGLAAAJ)), and a driverless Windows WebUSB channel would need a new vendor interface with MS OS 2.0 descriptors. That interface could live in the app rather than the bootloader, but Web Serial already covers the same hosts.

The real engineering work is the wire protocol, not the browser APIs. Web Bluetooth cannot request or read the ATT MTU, and one estimate puts 100 KB at about 8 s at MTU 23 versus under 1 s at 247 ([WebBluetoothCG #383](https://github.com/WebBluetoothCG/web-bluetooth/issues/383)). A base64 text protocol over 20-byte writes would take an estimated **2–5+ minutes** for the ~465 KB image. Binary, MTU-sized write-without-response with windowed notification acks should take about **15–60 s**. Web Serial with binary framing should take about **3–8 s**. These are arithmetic estimates and need bench numbers before any of them appear in UI copy. The firmware should report its negotiated MTU over NUS, accept offset-addressed chunks, and report its highest contiguous offset on reconnect so a dropped link resumes instead of restarting. mcumgr-web's auto-reconnect-and-resume shows the pattern ([mcumgr-web](https://github.com/boogie/mcumgr-web)). On Android, the page should hold a Screen Wake Lock for the whole transfer. Backgrounded or screen-off pages have historically throttled Bluetooth streams ([W3C log, 2020](https://lists.w3.org/Archives/Public/public-device-apis-log/2020Jul/0036.html)), and Meshtastic users report that iOS auto-lock interrupts uploads ([Meshtastic OTA](https://meshtastic.org/docs/getting-started/flashing-firmware/nrf52/ota/)).

The model to copy is ESP Web Tools and Flipper Lab. In both, one HTTPS page owns the protocol end to end with a manifest, device detection and a verify step, and both are used at scale by WLED, Tasmota and ESPHome ([ESP Web Tools](https://esphome.github.io/esp-web-tools/)). The device-side version of that is the app's own `ota` protocol, not the bootloader's.

## iPhone owners get updates through the hub before anything else

No iOS browser engine exposes Web Bluetooth, and a Chrome engineer reported in 2024 that WebKit "continues to be opposed" to generic peripheral APIs ([W3C list](https://lists.w3.org/Archives/Public/public-web-bluetooth/2024Sep/0002.html)). EU alternative engines have not changed this. As of June 2026 Blink on iOS was still a research prototype from Edge, and none of the Google or Mozilla prototypes had been released ([GIGAZINE](https://gigazine.net/gsc_news/en/20260618-blink-on-ios/)). Three realistic routes remain, and they differ in who bears the cost.

**Hub-driven OTA costs the owner nothing.** Personal devices already join the fleet's BLE broadcaster network when in range, and blinky-server already updates devices through `FleetManager.flash_device(force=False)`, which brings dedup, backoff, a persistent audit log and version-verify. Industry guidance treats unattended updates as the normal model for devices without a UI, gated by canaries, staged rollout and abort ([RFC 9019](https://www.rfc-editor.org/rfc/rfc9019); [Memfault deploy process](https://docs.memfault.com/docs/best-practices/ota-deploy-process)). Personal devices only run fleet-stable builds, so the installed fleet is already the canary cohort. The remaining work is policy. Owners need an opt-in flag, defaulting to on. Updates should be gated on battery and version. The hub should prefer the QSPI-staged NUS path over bootloader BLE DFU, which invalidates the app before the transfer completes. The limitation is reach: the hub only serves devices that come near it.

**Bluefy costs the owner one install.** It is free, rated 4.8★ on about 1.3K ratings, and has added `watchAdvertisements()`, `getDevices()` and a screen-dim control that helps keep long transfers alive ([App Store: Bluefy](https://apps.apple.com/app/id1492822055)). The beacio Safari extension injects `navigator.bluetooth` into Safari itself on iOS 26.2+, but it is new and unproven ([App Store](https://apps.apple.com/de/app/ioswebble/id6761301368)). No source confirms that either app can complete a ~465 KB NUS transfer reliably, so that is a bench question.

**A native app costs the maintainer the most.** It means US$99/yr for Apple, App Review, and upkeep for each OS release. Capacitor plus `@capacitor-community/bluetooth-le` could wrap the existing React console with almost no protocol changes. The plugin mirrors Web Bluetooth, falls back to web, and adds `getMtu` and Android connection priority on native ([capacitor bluetooth-le](https://github.com/capacitor-community/bluetooth-le)). An App Clip can use Core Bluetooth in the foreground, but it requires a full app to ship alongside it ([Apple App Clip docs](https://developer.apple.com/tutorials/data/documentation/appclip/choosing-the-right-functionality-for-your-app-clip.md)). Generic apps such as nRF Connect and nRF Device Firmware Update are not acceptable as the primary path. Meshtastic's docs pin users to nRF Connect 4.24.3 because the current DFU app "is not compatible", and forum reports describe iOS legacy DFU leaving nodes stuck in DFU mode ([Meshtastic OTA](https://meshtastic.org/docs/getting-started/flashing-firmware/nrf52/ota/); [Meshtastic forum](https://meshtastic.discourse.group/t/flash-node-from-iphone/11561)). Nordic's iOS and Android DFU libraries still support legacy DFU ([IOS-DFU-Library](https://github.com/NordicSemiconductor/IOS-DFU-Library); [Android-DFU-Library](https://github.com/NordicSemiconductor/Android-DFU-Library)), so a future native app could embed one as a rescue path for devices stuck in the bootloader.

A signed desktop helper app is the weakest option. Azure Artifact Signing limits individual developers to the US and Canada ([Microsoft Learn](https://learn.microsoft.com/azure/artifact-signing/quickstart)). EV certificates no longer grant instant SmartScreen reputation ([Microsoft Learn](https://learn.microsoft.com/et-ee/windows/apps/package-and-deploy/smartscreen-reputation)). Sequoia removed the Gatekeeper Control-click bypass ([Eclectic Light](https://eclecticlight.co/2024/08/10/gatekeeper-and-notarization-in-sequoia/)). Peer projects such as Betaflight are moving away from native desktop apps toward the web ([Betaflight](https://www.betaflight.com/docs/wiki/app)). Device-to-device propagation is also out. Standard Bluetooth Mesh DFU would require a Zephyr/NCS rewrite ([Nordic NCS](https://nrfconnectdocs.nordicsemi.com/ncs/latest/nrf/samples/bluetooth/mesh/dfu/distributor/README.html)), and a custom epidemic scheme spreads a bad image with no central abort.

## Opening NUS to web pages makes signing mandatory

Today the trust boundary is whoever can reach the device. The blocklist rationale applies directly: Chrome blocks legacy DFU because a malicious site could rewrite a device. NUS is unblocked because the browser assumes the device validates what it receives. Our device does not. It checks a CRC, which catches random corruption but not a crafted image. MCUboot and Nordic Secure DFU both check a SHA-256 hash and an optional signature before copying ([MCUboot design](https://docs.mcuboot.com/design.html)). Secure DFU's prevalidation checks hardware compatibility, SoftDevice requirement, firmware version, hash and signature, in that order ([nRF5 SDK Secure DFU](https://docs.nordicsemi.com/r/bundle/nrf5_sdk_v14.2.0/page/ble_sdk_app_dfu_bootloader.html)). RFC 9019 makes authentication and integrity mandatory for unattended updates ([RFC 9019](https://www.rfc-editor.org/rfc/rfc9019)).

The cheapest effective design does not touch the bootloader. The release pipeline produces a small manifest containing board ID, build number, image size, SHA-256 and an Ed25519 signature, signed by a key that lives offline. The app verifies the manifest's signature at `ota begin`, the hash at `ota commit`, and refuses a different board ID or a build number at or below its own. Only then does it set the apply flag. Build numbers are already the project's deployment source of truth, so anti-rollback is a comparison, with a separately signed emergency-rollback manifest as the only exception. This closes the malicious-page and nearby-attacker cases. Unsigned UF2 remains a bypass for anyone with physical USB access, which is acceptable for this threat model. Moving verification into the bootloader is stronger, because it protects against a compromised app, but it is a later phase under the bootloader rules.

Two power-loss questions need source review in the fork. GPREGRET survives soft resets but not power-off. If power drops mid-copy, the device reboots with the flag cleared and the internal app half-written. It then lands in UF2/BLE DFU mode, which is recoverable but not self-healing. Prior art handles this with a persistent "copy pending" marker and an idempotent restart of the copy from the still-intact QSPI image. 2 MB of QSPI would also hold a backup of the current app, which turns the existing app-handshake watchdog into MCUboot-style test/confirm. In that design, `markStable()` at 60 s confirms the new image, and three missed handshakes trigger a restore of the backup instead of only forcing DFU. The 60-second rule also binds the updater's UX. A page that retries a failed apply by rebooting quickly will trip the `RebootFrequencyCounter` quarantine. Retry logic must wait for at least 75 s of uptime between resets.

## Recommended plan

| Phase | Deliverable | Platforms reached | Safety gates | Bench-test first |
|---|---|---|---|---|
| 0 (now) | Keep the browser UF2 flasher off. Narrow `msc_uf2_check_stuck()` to arm only after the first valid UF2 block and reset only on valid blocks. Ship it through `deploy-bootloader.sh` | Technician recovery on Windows/macOS | `verify_bootloader.py` invariant; sacrificial device; 60 s spacing | Windows mount with no copy (SVI write) must not drop the drive; a full UF2 copy on Windows 11 and macOS Sequoia/Tahoe; 30-run soak like the 0.8.0-10 measurement |
| 1 | Signed manifest (Ed25519, board ID, build number, SHA-256) verified **in the app** at `ota begin/commit`; anti-rollback by build number; binary, offset-addressed, resumable chunk framing with MTU report | Prerequisite for everything below | Reject wrong signature, wrong board, downgrade, truncated image, hash mismatch; log `[FALLBACK]`-style errors loudly | Each rejection case over serial and NUS; interrupt the transfer at 10/50/99% and confirm the old app runs; resume after reconnect |
| 2 | One HTTPS page in the existing console: "Update over USB" (Web Serial) and "Update over Bluetooth" (Web Bluetooth NUS). It fetches only the fleet-stable release, shows current and target versions, holds a Wake Lock, and verifies the version after reboot | Windows/macOS/ChromeOS on Chrome/Edge (Serial + BLE); Firefox 151+ (Serial); Android Chrome (BLE) | Same as phase 1; refuse low battery; never auto-retry a reboot within 75 s | Measured transfer time and success rate on Chrome/Win11, Chrome/macOS, Edge/Win11, Firefox 151 Serial, two or three Android phones; screen-off and tab-switch behaviour on Android |
| 3 | Hub-driven auto-update: blinky-server offers the fleet-stable build to opted-in personal devices seen on the broadcaster network, via `flash_device(force=False)` using the NUS staging path | Every owner, including iPhone, whenever the device is near a hub | Opt-in flag; battery and version gate; build must have been stable on the installed fleet for N days; audit log; one-click pause | Device leaves range mid-transfer; two hubs in range; dedup and backoff across server restart |
| 4 | iPhone documentation: "Open this page in Bluefy" | iPhone/iPad (one extra install) | Same page and protocol | Full 465 KB transfer in Bluefy on current iOS with auto-lock on and off; check beacio on iOS 26.2+ |
| 5 (conditional) | Capacitor build of the console for the App Store (App Clip optional), with Nordic legacy DFU embedded as a rescue path; separately, bootloader-side signature check, persistent copy-pending marker, and QSPI backup/restore | Native iPhone and Android | Bootloader rules apply in full | Power cut during the bootloader copy; restore-from-backup after 3 missed handshakes |

Phases 0–2 are a few weeks of work and need no store accounts, no code-signing certificates and no fleet-wide bootloader replacement beyond the narrow stuck-check fix. Phase 5 should start only if hub coverage and Bluefy leave iPhone owners stranded in practice. That is a decision to make from support requests, not one to make in advance.

## Conclusion

The failed flasher was a sign that the update path should move up a layer, out of the bootloader and into the app. The bootloader's job shrinks to applying a verified, staged image and being a recovery fallback, which is the job it can do safely on sealed devices. Once the app owns the transfer, the browser APIs that actually ship (Web Serial and Web Bluetooth to NUS) cover every platform except iOS, and the fleet hub covers iOS owners without asking them to do anything. The new risk is the one the original design never had to face: a public web page plus an unauthenticated NUS endpoint turns "update" into "anyone nearby can reflash this". Signing and anti-rollback are therefore the first deliverable rather than a hardening pass. The biggest unknowns are all measurable. They are real NUS throughput in each browser, Bluefy's reliability on large transfers, Android's wired Web Serial rollout, and the fork's behaviour on power loss mid-copy. Each has a bench test in the plan above, and the results should set the UI promises.
